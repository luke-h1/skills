# Appeeky Spec

The app's store listings live in files, and every push is recorded and measured.

| Path | What it holds |
| --- | --- |
| `appeeky.spec.yaml` | app, stores, `targets` (searches the app should be found for, per storefront), optional `storefronts` and `personas` |
| `appeeky/store/app-store/<locale>.yaml` | name, subtitle, keywords, promotionalText, description, whatsNew, supportUrl, marketingUrl |
| `appeeky/store/google-play/<language>.yaml` | title, shortDescription, fullDescription, video (Play codes like `tr-TR`) |
| `appeeky/releases/<id>.yaml` | every push: before/after values, note, rank baseline, day-7/14 checks |
| `appeeky/experiments/<id>.yaml` | screenshot, UGC, ads and pricing experiments |
| `appeeky/loops.md` | generated by `status`, `verify`, `push` and `experiment`: every change being measured, its metric, next check and result so far |
| `appeeky/playbook.md` | what worked and what did not for this app |
| `appeeky/reviews/` | customer reviews per month (JSONL), `summary.md`, and `replies/` drafted for review |
| `appeeky/competitors/<name>.yaml` | each competitor's listing, best ranks, ranks on your targets, recent low ratings |
| `appeeky/visibility/<country>.yaml` | whether ChatGPT, Claude, Gemini and Perplexity name the app per intent, who they name instead, the pages they cite, suggested fixes; `changes.md` beside it (`history.csv` and `answers/` with `--local` scans) |
| `appeeky/seo/` | Google Search Console for the app's website: `daily.csv`, `queries.csv`, `pages.csv`, `summary.md` (`seo pull`) |
| `appeeky/category.csv` | rank in the category chart (top 100), one row a day |
| `.appeeky/data/*.csv` (or `appeeky/data/`) | analytics, Search Ads, RevenueCat, Meta and TikTok per day; `README.md` says what each file holds |

Run commands as `npx @appeeky/spec <command> --json` (or `appeeky-spec` when installed). Add `-C <dir>` when the spec is not in the current folder.

## No spec yet

In a terminal the user runs, `init` with no options is a guided setup. It finds the app, pulls both stores, suggests targets, offers the workflows and the skills, and shows the first coverage. As an agent, use the flags instead:

1. Find the App Store app id and Google Play package name (Xcode project, `app.json`, `build.gradle`), or ask.
2. Store access: `appstore` / `gps` CLIs with the user's keys (local), or `APPEEKY_API_KEY` with a store connected in Appeeky (hosted). Do not ask for or handle key files yourself.
   - Local App Store: `appstore accounts add`, or `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_PRIVATE_KEY`.
   - Local Google Play: `gps accounts add`, or `GPS_CREDENTIALS`.
   - `--via auto` (default) uses a local CLI when installed, hosted when `APPEEKY_API_KEY` is set. `APPEEKY_API_KEY` also adds keyword popularity and ideas.
3. `init --name "<App>" --app-store <id> --google-play <package> --pull`, then fill `targets` (see appeeky-spec-targets).
4. `doctor --json` lists everything still missing (store access, targets, the key, attribution, workflows, skills, `.gitignore`), each with its fix. Exit code 1 means something must be fixed.

### Automation

`init --ci` (also on an existing spec) writes three GitHub workflows:

| Workflow | When | What |
| --- | --- | --- |
| `listing-check.yml` | every pull request | comments what the listing changes do (`report`), fails on check errors |
| `listing-push.yml` | merge to main touching `appeeky/store/**` or the spec | `push --yes`, then commits the release file |
| `listing-daily.yml` | daily 06:00 UTC | `category pull`, `visibility pull`, `verify --playbook`, `reviews pull`, `competitors pull`, `social pull`, `ugc pull`; `seo pull` with `GSC_CREDENTIALS` and `visibility scan --local` every `VISIBILITY_EVERY` days; then commits |

The merge is the approval gate: nothing reaches the store unless a person merged it. The workflows need `APPEEKY_API_KEY` (or store keys) as repository secrets.

Without GitHub Actions the same commands run anywhere:

- **Other CI** (GitLab, Bitbucket, CircleCI): the same three triggers and commands.
- **cron or launchd** on the user's machine: `examples/weekly/` has a script.
- **The user's own server** (or Railway, Fly, Render): `docker/docker-compose.yml` with a `.env` from `docker/.env.example`, then `docker compose up -d`. It runs the routines on a schedule and commits back. Its push routine only pushes listing changes that reached `main` after it started, so the merge stays the gate. Suggest `PUSH_DRY_RUN=1` for the first days.
- **A scheduled agent:** it runs the daily commands and the weekly routine below.
- **By hand:** `status` flags checks that are late.

Without CI, a person runs `push`. Never take over that gate with `--yes`.

## Workflow

1. **Understand.** Run `status` (or read `appeeky/loops.md`; `status --json` lists the `free` stores): do not start a change on a store that already has a release being measured, or the two results mix. Read `appeeky/playbook.md` and recent releases (`log --json`). Do not repeat a change that already lost unless something changed. With `APPEEKY_API_KEY`, refresh and read what users and competitors say: `reviews pull` then `appeeky/reviews/summary.md`, `competitors pull` then `appeeky/competitors/`, `visibility pull` then `appeeky/visibility/`, and `data pull` for the numbers (`.appeeky/data/README.md`). `category pull` records today's category rank (the App Store needs no key). Words users use in reviews and searches competitors win are good candidates for targets.
2. **Find gaps.** `coverage --json`, `suggest --json` and `check --json`. Missing or `partial` high-popularity targets are the opportunities. `crossLocalization` lists extra locales a storefront reads with spare keyword space. If listings are missing, run `pull` first.
3. **Propose.** Edit the listing files. Keep every word that currently covers a target unless the user agrees to drop it. For each change say which targets it should gain and which it could lose. One clear hypothesis per release.
4. **Verify.** `check --json` (no errors allowed) and `diff --json`. Changes marked `blocked` cannot go live yet; tell the user why (usually: the App Store needs a new version, `push --create-version <x.y.z>`).
5. **Ship only with consent.** Pushing changes the live store; on Google Play it is public within minutes. Run `push --note "<hypothesis>"` only when the user asked; use `--yes` only when they said so explicitly. Commit the release file it writes.
6. **Learn.** After day 7, `verify --playbook --json` (see appeeky-spec-review).

Never run `pull` over uncommitted listing edits: it overwrites local files.

### Weekly routine: the co-founder review

For a scheduled or "what should we do this week" run, follow the co-founder review: `agents/cofounder.md` in this package, installed as the `/appeeky-cofounder` command by `agents install`.

1. `status --json`: only the `free` stores may change. Read `appeeky/loops.md`, `appeeky/playbook.md` and the latest brief in `appeeky/briefs/`.
2. Start the specialist subagents in parallel: `appeeky-aso`, `appeeky-reviews`, `appeeky-ads`, `appeeky-releases`, `appeeky-ugc`, `appeeky-social`. They only read, and each returns findings and up to two candidate changes. Without subagents, do their checklists yourself.
3. Pick exactly one change for a free store, the one with the strongest evidence. Never repeat a change the playbook says lost.
4. Edit, then `check` and `diff`.
5. Write the brief to `appeeky/briefs/<date>.md`: where things stand, what each specialist found, the change (or why none), what is for a person (replies, ads, product requests, the next UGC experiment, posts to publish), and what was not picked.
6. Write `.appeeky/proposal.md` for the pull request. Do not `push`. A person merges; the push runs on merge.

`npx @appeeky/spec agents install` writes the specialists and the command into `.claude/` (`--for opencode` or `all` for `.opencode/`). Commit them so scheduled runs have them too.

To run it every week without anyone starting it:

| Where | How |
| --- | --- |
| GitHub Actions | `examples/weekly/appeeky-spec-weekly.yml` |
| The user's machine | `examples/weekly/weekly.sh` with cron or launchd |
| The user's own server | `WEEKLY_AT=0 7 * * 1` in the docker `.env`, with the `latest-agent` image |

Each uses `.github/appeeky-propose.md` when it exists, otherwise the installed `.claude/commands/appeeky-cofounder.md`. The pull request carries the brief, and the listing change when there is one.

The agent needs one of two things:
- **`CLAUDE_CODE_OAUTH_TOKEN`:** the user runs `claude setup-token` once on their computer. Runs then count against their Claude Pro or Max plan, with no API key.
- **`ANTHROPIC_API_KEY`:** billed per use.

Set it as a repository secret or in the `.env`. Never ask the user to paste a token into chat or commit it.

### Before and after a change

- `competitors discover --add <n>` finds apps like this one and adds them to `competitors:`.
- `report --base main` prints the Markdown a pull request needs: listing changes, check results and coverage.
- `log --markdown` summarizes past releases.

## App Store rules

- Name 30, subtitle 30, keyword field 100, promotional text 170 characters. Counted in characters, not bytes (a Cyrillic or CJK letter is one).
- Name, subtitle and keyword field words are indexed once and combine into phrases across the three. Never repeat a word across them. Separate keywords with commas and no spaces; a field without commas is read as one phrase.
- Weight: name > subtitle > keyword field. The description is not indexed for search.
- Skip filler words ("app", "the", "and", "for"), the app's category name and plurals of words already present (English).
- Only promotional text changes without a new version.
- A storefront can index more than one listing locale (the US App Store also reads Spanish (Mexico)). Use the extra locale's keyword field for more keywords for that storefront; `coverage` counts it.
- Do not use competitor brand names or trademarks.

## Google Play rules

- Title 30, short description 80, full description 4000 characters. All three are indexed; use the main keywords naturally in the full description, without stuffing.
- No ranking or promotional words ("best", "#1", "top", "free", "sale"), emoji or all caps in the title.
- Changes go live without an app update. A new language needs all three text fields.

## Screenshots

`screenshots pull` downloads the live App Store screenshots of every locale into `appeeky/screenshots/app-store/`. `screenshots check` (also part of `check`) flags wrong sizes and counts per display type. Screenshots are not indexed for search; they change conversion, so treat a new set as an experiment.

## AI visibility and category rank

Whether ChatGPT, Claude, Gemini and Perplexity name the app (`aiVisibility:` in the spec, `visibility init|sync|pull`), and the daily category chart rank (`category pull`): see appeeky-spec-visibility. Never run `visibility sync --prune` or `visibility scan` unless the user asked.

## Reviews

`reviews list --rating 1-2 --unanswered --json` shows what needs an answer. Draft each reply with `reviews reply <id> --text "..."`: specific to what the user said, no promises the app does not keep, under 350 characters for Google Play. The drafts land in `appeeky/reviews/replies/`; open a pull request with them and send them with `reviews push` only after it is approved. Recurring complaints in reviews are listing input too: a feature people look for belongs in the description or the screenshots.
